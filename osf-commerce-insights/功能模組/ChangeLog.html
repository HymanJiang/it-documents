發現的問題

第六次修改（2026-06-11）— Store 資料權限（簡化版）

背景與決策

報表頁面要依登入者權限限制可看資料。曾評估「Region 權限」,但因 Region 是階層中間層,受限使用者的 Level 1 數字需「只加總可看 Region」→ 必須重算,且其分量來自無法修改的 PBI_OSF_Commerce_Performance,複雜度高(一度建了「存原始、讀取時算」的 Raw 表 + 兩支新 SP,後因故放棄)。

最終改用 Store（階層最外層 Level 1）作為權限維度,複雜度大幅下降:
- Store 是最外層,所有預存的 ALL 彙總列本來就「每個 Store 各自一份」→ 完全不需要重算,只要過濾「顯示哪些 Store 的列」。
- 完全沿用現有資料管線(SP_OSF_CommerceInsights 寫入 + OSF_CommerceInsights 預存表),不新增任何 DB 物件、不改任何 SQL。

註:先前嘗試的 OSF_CommerceInsights_Raw、SP_OSF_CommerceInsights_LoadRaw、SP_OSF_CommerceInsights_Get 已全部移除(檔案已刪)。若先前曾在 DB 建立這些物件,可一併 DROP:

第四次修改（2026-05-21）

一、修正 SP_OSF_CommerceInsights.sql（兩項）

修正 1：YTM SUM 無法命中 Shipment KPI（名稱 template vs 實際年份不符）

  • 問題：OSF_CommerceInsightsKPI 設定表存的是 template 名稱（LastYear Actual (K)、CurrentYear Achv. (K)），但 SP 執行時已將它們替換為實際年份（如 2025 Actual (K)、2026 Achv. (K)）；YTM SUM 的 IN 子查詢從設定表取出 template 名稱，對不上 #Temp_YtmMonthly 的資料，導致這兩個 KPI 的 YTM 完全不計算。
  • 修正：IN 子查詢加 CASE WHEN [KPI] LIKE '%LastYear%' THEN REPLACE(...) WHEN [KPI] LIKE '%CurrentYear%' THEN REPLACE(...) ELSE [KPI] END，將 template 名稱動態轉成實際年份名稱再比對。

修正 2：ROAS 的 YTM 分母應為 ADEX (K) * 1000

  • 問題：原公式 CurrentYear Achv. (K) / ADEX (K)，ADEX 單位為千元，需乘以 1000 才與分子單位一致。
  • 修正：[Revenue] / NULLIF([Adex] * 1000, 0)；comment 同步更新。

修正 3：New Customer % 的 YTM 分母應為 AVG(Accu Member #)，而非 SUM

  • 問題：原設計依賴後續 New Customer % 區塊「自動」計算 YTM，但該區塊直接用 #Temp_OSF_CommerceInsights 裡的 YTM 列（Accu Member # YTM = SUM of monthly），導致公式變成 SUM(New Registrant #) / SUM(Accu Member #)，分母不正確。
  • 正確公式：AVG(New Registrant #) / AVG(Accu Member #)（分子分母皆取各月平均值）。
  • 修正（SP step ④ RECALC_AVG）：
  • 在 DROP TABLE #Temp_YtmMonthly 之前，新增 [NewCustomerYtm] CTE，從 #Temp_YtmMonthly 用 AVG/AVG CASE 分別彙總，INSERT YTM 的 New Customer % 紀錄。
  • New Customer % 區塊的兩個 CTE 加 AND [DateDimension] <> 'YTM'，防止它再用 SUM/SUM 重複計算一筆錯誤的 YTM。

報表架構理解

資料來源

資料 來源
Shipment（出貨量/金額） [ACLSTNR11].[ACLDW].[dbo].[vw_SalesData_BomExpand_LocalRevenue_IoTMart]
其他 KPI（Lead、GP%、AOV 等） [ACLPBI].[dbo].[PBI_OSF_Commerce_Performance]
KPI 定義與樣式 [OSF_CommerceInsightsKPI]（靜態設定表，無 HierarchyYear）
層級結構 [OSF_CommerceInsightsHierarchy]（有 HierarchyYear，Level 1/2 人工維護，Level 3 由 SP 動態產生）
彙整結果 [OSF_CommerceInsights]（SP 執行後寫入，頁面讀取此表）

SP 執行流程

1. 清空 #Temp_OSF_CommerceInsights
2. 撈 Shipment 原始資料（UNPIVOT 多幣別）→ #Temp_Shipment
3. 產生 Shipment 7 層級彙總（Store/Region/Country 各種 ALL 組合）→ 含 Total（Month=99）
4. 撈 PBI KPI 資料（依 DataSource 篩選）
5. 合併 PBI + Shipment INSERT 進 #Temp
6. 計算 YTM（加總月份 < 當月）
7. 計算 YoY Growth %（CurrentYear Shipment / LastYear Shipment - 1）
8. 計算 New Customer %（New Registrant # / Accu Member #）
9. 動態更新 OSF_CommerceInsightsHierarchy Level 3（Country，從實際資料產生）
10. DELETE + INSERT OSF_CommerceInsights（以 HierarchyYear 為單位替換）

前端層級邏輯

Store 未選     → Level 1（維度欄 = Store，資料條件：Region=ALL, Country=ALL）
Store 已選     → Level 2（維度欄 = Region，資料條件：Store=選取值, Country=ALL）
Store+Region 選 → Level 3（維度欄 = Country，資料條件：Store=選取值, Region=選取值）

表格結構

  • 第一列：幣別、Q1/Q2/Q3/Q4 群組、Year Total、YTM Total、YTM Local
  • 第二列：Store/Region/Country、Performance Area、KPI、Jan~Dec
  • Dimension Value 欄 rowspan = KPI 總數，Level 1/2 可點擊下鑽
  • Performance Area 欄 rowspan = 該 PA 的 KPI 數
  • KPI 欄套用 backgroundColor / fontColor / Floor×10px padding

設定資料（設定檔.xlsx）

  • OSF_CommerceInsightsKPI：29 筆 KPI 定義，欄位包含 PerformanceArea、KPI、Sort、FontColor、BackgroundColor、Floor、DecimalPlaces、hasLocalCurrency、hasPercentage、DataSource
  • OSF_CommerceInsightsHierarchy：含 2024/2025/2026 三年，Level 1（7 個 Store）、Level 2（13 個 Region）、Level 3（由 SP 動態產生）
