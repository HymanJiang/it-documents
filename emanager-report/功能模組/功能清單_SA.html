eManager ScoreCard — 共用報表框架

eManagerReport 功能規格

本文件說明 eManagerReport 共用框架的功能範圍、設計邏輯與資料模型，供 SA 在理解現有系統、評估擴充需求或設計新報表時參考。

系統 eManagerCore (.NET Core)
資料庫 EMGRV2（結構）、MFG / ProjectReport（資料）
ORM Dapper

🎯 設計目標與原則

eManagerReport 的核心設計目標是：讓任何新報表都能在不修改程式碼的前提下上線，透過資料庫設定驅動報表的所有結構與行為。

原則 01

DB 驅動，零程式碼新增報表

報表的層級數、KPI 欄位、組織單位列、時間維度、顯示規則、權限設定，全部透過 DB 設定，不需改任何 C# 或 JS。

原則 02

共用框架，各報表結構獨立

所有報表共用同一套程式邏輯，但每張報表透過 ReportID 完全隔離，結構互不影響，可以各自設定不同的層級、KPI 與維度。

原則 03

資料來源可擴充

現有框架支援三種資料來源（OSF / HC Dashboard / CRM），接入新資料來源需在 Repository 新增查詢方法和 Service 新增對應分支，不影響現有邏輯。

原則 04

權限從資料庫讀取，不寫死

三層權限（Level / Measure / KPI）均透過 DB Views 和資料表設定，管理員可隨時調整，不需 Redeploy。

✦
什麼需要改程式碼：新增資料來源（Repository + Service case）、新增零值過濾條件、新增 SpecialKPI 計算邏輯。
什麼只需設定 DB：新增/修改報表、調整層級/KPI/維度/Measures、設定所有類型的權限。

🗄️ 資料模型（DB 設定層）

以下為 EMGRV2 資料庫中報表結構相關的資料表，全部透過 ReportID（Guid）關聯到同一張報表。

📋 Report_Basic

報表的基本資訊與全域設定，一張報表一筆。

  • ReportIDPK Guid
  • ReportCode OSF / HC Dashboard / CRM / ...
  • Name 報表顯示名稱
  • ReportType Classic / MultipleReportView
  • MaxLevel 最深層級數
  • isDefaultLevel 是否依權限決定預設層
  • StartYear 報表起始年份
  • CurrencyUnitRemark 幣別單位備註文字
  • RedirectText 外連按鈕文字（可空）
  • RedirectUrl 外連 URL，支援佔位符
🗂️ Report_Level

定義報表的層級結構，每層一筆。

  • ReportID FK
  • Level 層級編號（1, 2, 3...）
  • LevelColumnName 對應資料來源的欄位名稱
  • FilterName 篩選器顯示名稱
  • ShowFilter 是否顯示此層篩選器
  • hasPermission 此層是否啟用 Measure 權限
📅 Report_Dimensions

報表橫軸的時間維度欄位群組，每個維度一筆。

  • ReportID FK
  • Name 維度名稱（Jan / YTD / ...）
  • GroupName 群組名稱
  • Sort 排序
  • DisplayGroup 顯示群組
  • IsDefault 預設是否顯示
🏷️ Report_Measures

報表縱軸的組織單位清單（依 Year 分版本）。

  • ReportID FK
  • Level 所屬層級
  • Name 組織單位名稱
  • Year 對應年份
  • Sort 排序
  • FontColor / BackgroundColor 樣式
  • ParentName 父層名稱
  • DisplayGroup 顯示分組
  • FilterColor 篩選器標籤顏色
📊 Report_Measures_KPIs

KPI 欄位定義，每個層級的 KPI 各為一筆。

  • ReportID FK
  • Level 所屬層級
  • Name 資料比對用名稱（可含佔位符）
  • DisplayName 顯示名稱
  • Sort / Unit / DecimalPoint 格式
  • FontColor / BackgroundColor 樣式
  • CompareCategory / CompareType / Compare / CompareStyle 比較規則
  • URL 點擊連結
  • Permission 是否啟用 KPI 層級權限
  • needEmpty 後方插入空白分隔列
  • CurrentMonthZero 當月歸零
  • IsDefault 預設顯示
  • PastMonthsAdjustment / FutureMonthsAdjustment 月份調整
⚠️ Report_Measures_KPIs_SpecialRule

特定 Measure × Dimension 組合的覆蓋顯示規則。

  • ReportID FK
  • KPIName 對應的 KPI 名稱
  • Dimensions 對應的維度名稱
  • SpecialRule 規則類型
  • DisplayValue 覆蓋顯示文字
🔒 Report_Measures_KPIs_Permission

KPI 層級的個人或通用權限設定。

  • ReportID FK
  • Level 所屬層級
  • Email 空 = 通用規則；有值 = 個人規則
  • Name KPI 名稱
  • LastLevelMeasures 空 = 不限制；有值 = 需符合條件
  • CheckLevel 空 = Level-1；有值 = 指定對照層
  • Measures 授權可見的 Measure（空 = 不限制）

DB Views（唯讀，由框架查詢）

View 名稱用途關鍵輸出欄位
vw_Report_Level_Permission使用者的 Level 存取權限DefaultLevel、RequiredPermissionLevels
vw_Report_MeasuresMeasures 清單（含年份對應邏輯）同 Report_Measures 欄位

🔢 Level 決定邏輯

每次請求，Service 層依下列邏輯決定本次顯示的 Level，結果寫回 ReportFilter.Level：

// 情況一：初次載入（無 MeasuresValue） if isDefaultLevel == true: Level = levelPermission?.DefaultLevel ?? 0 // 無權限記錄 → 0 = 無存取權 else: Level = 1 // 情況二：使用者已選擇（有 MeasuresValue） foreach level in MeasuresValue.Keys (升序): if MeasuresValue[level] == "ALL" → Level = level; break if 沒有找到 "ALL" → Level = MaxLevel // 套用 Level 權限限制（兩種情況都會執行） if levelPermission != null: Level = RequiredPermissionLevelsList .Where(x => x >= Level) .OrderBy(x => x) .FirstOrDefault() // 找到 ≥ 當前 Level 的最小授權層 // Level = 0 → 回傳空報表，停止後續查詢
ℹ
Level 決定後，才執行 Dimensions / Measures / KPIs / 資料查詢。Level = 0 時直接回傳空的 Report 物件，不查詢後續資料。

🔒 三層權限架構

框架的權限採三層疊加設計，每層獨立、各自可開關：

Layer 1
Level 權限

控制使用者可存取的層級範圍

決定使用者進入報表的預設層（DefaultLevel），以及可以切換的層級清單（RequiredPermissionLevelsList）。
DefaultLevel = 0 → 無存取權，回傳空報表。

來源：vw_Report_Level_Permission
Layer 2
Measure 權限

控制使用者在每個層級可見的組織單位列

需在 Report_Level.hasPermission = 1 時才啟用該層過濾。
包含 "ALL" → 顯示全部；無 "ALL" → 只顯示授權名稱；無任何記錄 → 顯示全部（不限制）。

來源：vw_Report_Measures_Permission
Layer 3
KPI 權限

控制使用者可見的 KPI 欄位

需在 Report_Measures_KPIs.Permission = 1 時才啟用。支援靜態設定（指定 Email 或通用）與動態設定（依使用者在指定層的選擇值決定）。
個人規則（Email 有值）與通用規則（Email 空值）透過 UNION ALL 合併後一起評估。

來源：Report_Measures_KPIs_Permission

⚙️ KPI 動態權限邏輯

Layer 3 的 KPI 權限支援依「使用者在指定層的選擇值」動態決定顯示，設計如下：

// KPI.Permission = false → 永遠顯示 // KPI.Permission = true → 進入以下判斷 var userPermissions = GetPermissions(ReportID, Email, Level) // = 通用規則(Email='') UNION ALL 個人規則(Email=@Email) if userPermissions 中有任一筆 LastLevelMeasures 為空: LastLevelDimensionCheck = true // 不限制，顯示 else: LastLevelDimensionCheck = userPermissions.Any(p => checkLevel = p.CheckLevel ?? (reportFilter.Level - 1) selectedValue = MeasuresValue[checkLevel] // 使用者在該層的選擇 if 使用者尚未在 checkLevel 做選擇 → true // 預設開放 else selectedValue == p.LastLevelMeasures → true )
⚠
View 端需根據 KPI.LastLevelDimensionCheck 旗標決定是否渲染該 KPI 欄。此旗標已在 Service 層計算完成，View 端不需重複判斷邏輯。

🔌 資料來源接入模式

新增資料來源需實作以下步驟，現有三個資料來源皆遵循同樣的模式：

步驟位置說明修改範圍
1. 定義資料來源 Model eManagerCore.Models/DataModels/eManager/ReportSource/DataSource/ 對應資料表欄位的 C# 類別 改程式
2. 新增 Repository 方法 ReportSourceRepository.cs 實作 Dapper 查詢，接收 ReportFilter 和 FilterColumn 改程式
3. 在介面宣告 IReportSourceRepository.cs 新增對應的 interface 方法 改程式
4. 在 Service 新增 case ReportStructureService.GetReportSources() 在 switch (ReportCode) 新增分支，將查詢結果轉為 ReportSourceItem 清單 改程式
5. 設定 Report_Basic EMGRV2 DB 新增報表記錄，ReportCode 設為 step 4 新增的 case 名稱 設定 DB

FilterColumn 的建立邏輯

GetReportSources() 在呼叫資料來源前，會依目前的層級選擇狀態建立 FilterColumn（Dictionary<string, List<string>>），key 為 Report_Level.LevelColumnName，value 為要傳入 SQL IN 條件的值清單。資料來源 Repository 直接用這個字典組出 WHERE 子句，不需自行判斷層級邏輯。

ℹ
FilterColumn 的 value 為空 list 時，框架不會加入 WHERE 條件（即不過濾該欄位）。實作 Repository 時依此約定即可。

🔄 KPI 名稱動態轉換

Service 層在 GetReportKPI() 中依 reportFilter.Year 建立轉換字典，對 DB 中的 KPI Name 執行轉換後才回傳給 View：

DB 中設定的 Name轉換後（Year = 2025）用途
CurrentYear Quota2025 Quota當年目標
CurrentYear Achv.2025 Achv.當年達成
CurrentYear Backlog2025 Backlog當年未出貨
LastYear Actual2024 Actual去年實績
CurrentYear Digital Actual %2025 Digital Actual %
LastYear Digital Actual %2024 Digital Actual %
2025Shipment（含年份）2025 Achv.OSF 特有格式
2024Shipment2024 Actual

DisplayName 同步規則：若 DB 中 DisplayName == Name，轉換後 DisplayName 也跟著更新；若兩者不同，DisplayName 保持不變，只有 Name 做資料比對用的轉換。

⚠
Non-Breaking Space 問題：DB 中若 KPI Name 混入 Unicode 字元碼 160（外觀與空白相同），轉換字典的 key 比對會失敗，導致年份轉換不套用。框架在 TransformKPIName() 中已加入 normalize（替換字元碼 160 並 Trim），但若發現 KPI 名稱未正確轉換，應先確認 DB 中是否有此字元。

🧹 資料清理機制

GetReportSources() 建立 FilterColumn 後，執行以下清理：

清理項目原因處理方式
字串 "null" 前端未選擇時可能傳入字串 "null"，若帶入 SQL IN 條件會產生無效查詢 從 filterColumnValue 中移除
值含 "all"（不分大小寫） 統一規格化，避免大小寫差異造成邏輯不一致 整個 filterColumnValue 簡化為 ["ALL"]

🚫 零值列自動過濾

特定報表取得資料後，過濾在關鍵 KPI 上全年合計為零的 Measures 列，避免報表出現無意義的空白行。過濾後只影響當前 Level 的列，其他 Level 的列保留。

目前觸發條件寫死在 Service 層，新增需修改程式碼：

觸發依據觸發值過濾 KPI過濾維度
Report_Basic.Name"Sales Performance"{Year} Achv.Year Total
Report_Basic.ReportCode"HC Dashboard"RevenueYTM
Report_Basic.ReportCode"CRM"AchivementYear Total

🔗 RedirectUrl 佔位符替換

Report_Basic.RedirectText 和 RedirectUrl 同時有值時，View 上會顯示一個導向按鈕。NewReportStructure() 在傳入 View 前，先替換 URL 中的佔位符：

佔位符替換來源用途
{Email}reportFilter.Email（displayEmail）帶入使用者 Email，供目標系統識別身份
{EZTicketId}User.FindFirstValue("EZTicketId")帶入 EZTicket SSO Token，實現免登入跳轉
ℹ
替換後的 URL 直接寫入 Report.ReportBasic.RedirectUrl，View 端直接使用此值，不需再做處理。ReportUser.EZTicketId 也同時存入 Report.User，供 View 其他用途使用。
