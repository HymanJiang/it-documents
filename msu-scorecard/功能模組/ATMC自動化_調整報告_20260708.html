二、執行效能優化

問題

SP 全跑約 8 分鐘，瓶頸在 4 支跨 linked server 的 DENODO 遠端查詢。其中 3 支（DENODO-PROD）遠端條件寫 >= 今年-1（抓 2 年），但程式在本機一律 WHERE [YEAR_ID]=@Year，前一年資料 100% 被丟掉＝每次白抓一整年（含最大的 MOPEX 明細表 ksb1_opex_all）。

調整

將 3 支查詢改為用 sp_executesql 把 @Year 下推到遠端，只抓當年：先抓進本機暫存表（#Mopex_Raw / #Zrpp89_Raw / #Kp27_Raw），再把原 OPENQUERY(...) 換成讀該暫存表。原有的 CASE / 轉換 / UNPIVOT / CTE 邏輯完全未動。

附帶修正一個隱藏問題：遠端原本寫死 >= 今年-1，會讓 EXEC ...,2024 這類歷史年重跑撈空；改 = @Year 後歷史年重跑也正確。

  • 預期效益：3 支查詢遠端傳輸量大致砍半以上（少抓一整年；MOPEX 另可再評估下推 @Month）。實際改善幅度請用計時工具量測。

五、MOPEX % NO ROW — 根因調查

比對測試中 MOPEX % 與 MOPEX %(Exclude Internal PV) 皆 NO ROW。逐層追查結論：

sharepoint 來源 (bv_sharepoint_emanager_atmu_scorecard) 2026 共 16 列
   → Plant 欄、KPI 欄「全部為 NULL」（僅月份數字有值）
   → SP 以 [Plant] LIKE '%ATMC%' 過濾 → 一列都插不進 Temp
   → Temp 內無 Production Value(K)（此為唯一來源）
   → MOPEX % = MOPEX(K) INNER JOIN Production Value(K) → 右邊空 → 產 0 列
定性：非 SP bug、非命名文字差異、與本次效能改動無關（此 KPI 從最早的第一次比對就是 NO ROW）。欄位名稱正確（就叫 Plant/KPI），但值在來源就是 NULL，故改 SP 比對字串無效。
須在來源端修：SharePoint scorecard 清單或 Denodo view 的 Plant/KPI 欄位對應壞了／未填。建議再撈 WHERE [Year]=2025 判斷是「2026 這批壞掉」還是「一直未運作」。此項屬 #2/#3 連動、須來源端處理。
